# Hydration Sensor Firmware: Coding Standards

These standards describe what correct, readable, and maintainable code looks like in this
repository. They apply to the Zephyr / nRF Connect SDK firmware in `firmware/` (C11, nRF52840)
and its ztest suites in `firmware/tests/`.

They do not replace design review, tests, or the Zephyr and nRF documentation. Their job is to
make routine decisions predictable and to make exceptions visible.

## 0. How to read this document

**MUST** is a rule. **SHOULD** is the default; a deviation needs a stated reason in the commit or
PR. **MAY** is an allowed option.

**Order of authority when sources disagree:**

1. Correctness and safety of the device (watchdog, battery, measurement lockout).
2. The checked-in tool configuration: `.clang-format`, `.gitattributes`, and the CI workflow
   (`.github/workflows/ci.yml`).
3. This document.
4. Existing code nearby.

Existing code is not a precedent. If you find that this document and a tool configuration
disagree, fix one of them in its own commit. Do not choose whichever is more convenient.

Legacy code that breaks a rule here MAY stay as it is until you touch it. Code that you add or
change MUST follow the rules.

## 1. Core principles

### 1.1 Correctness before cleverness

- Code MUST do what its documentation says, on the real board and on `native_sim`.
- Prefer the plain implementation. Do not hide ordering, lifetime, or failure behind compact
  tricks.
- Do not add states, layers, Kconfig options, or caches without a real consumer.
- Make invalid states hard to represent: use enums instead of magic integers, and keep module
  state private.
- Check inputs at the boundary where they enter the system (shell commands, ADC readings, BLE
  writes, stored data).

### 1.2 Failures are values, contract violations are bugs

There are two kinds of "wrong":

| Kind | Example | Mechanism |
|---|---|---|
| Expected runtime failure | ADC not ready, flash write fails, BLE link lost, bad shell argument | Return a negative errno and handle it |
| Contract violation (programmer error) | FSM entered a state from an illegal predecessor, index out of range from internal code | `__ASSERT()` |

- Do not use `__ASSERT()` to check input from hardware, users, or radio. Asserts are compiled out
  when `CONFIG_ASSERT=n`.
- Do not return an error code to paper over a programmer error.
- Never report success (`return 0`) when the work was not done.

### 1.3 Make ownership, lifetime, and context visible

For every piece of state, a reader must be able to answer:

- **Owner:** which module (`.c` file) owns it?
- **Lifetime:** is it static for the whole run, or does it become invalid (for example a buffer
  that a callback borrows)?
- **Context:** which execution contexts touch it: ISR, a specific thread, the system work queue,
  a timer expiry function?
- **Protection:** what lock or atomic protects it, if more than one context touches it?

Function names, types, and Doxygen comments SHOULD answer these without reading the
implementation.

### 1.4 Small interfaces, cohesive modules

- A module exposes functions, not variables. Keep state `static` in the `.c` file.
- Expose the smallest API that current callers need.
- Keep pure logic separate from hardware access, so you can test it on `native_sim`
  (`batt_classify()` in `safety/battery.c` is the model to follow).
- Lower-level modules (`ui/`, `safety/`, `common/`) SHOULD NOT depend on higher-level ones. The
  one allowed upward path is posting events to the FSM with `fsm_post()`.

### 1.5 Optimize from evidence

- Correct first. Then measure (current draw, stack usage with the thread analyzer, timing) before
  you optimize.
- Battery life is the main performance budget. Prefer designs that let the CPU and peripherals
  sleep over designs that poll.
- Write down any non-obvious optimization and the measurement behind it.

## 2. Formatting

### 2.1 The formatter is the authority

- The root `.clang-format` defines C formatting. CI runs **clang-format 18.1.8** with `--Werror`
  on every tracked `*.c`, `*.h`, `*.cpp` and `*.hpp` file. Use the same version locally:

  ```bash
  pipx install clang-format==18.1.8
  ```

  ```bash
  git ls-files '*.c' '*.h' | xargs clang-format -i --style=file
  ```

- Do not fight the formatter with manual alignment or `// clang-format off`. If a construct truly
  needs it (a lookup table, a devicetree macro), keep the off/on pair tight around that
  construct and explain why in a comment.
- To change a formatting rule, change `.clang-format` in its own commit and reformat in that same
  commit. Do not mix that with functional changes.

### 2.2 What the formatter enforces (summary)

The configuration file wins if this summary is out of date.

- 4-space indent, no tabs, 100-column limit.
- Linux brace style: function braces on their own line; braces for `if`/`for`/`while`/`switch` on
  the same line.
- `InsertBraces: true`: every control-flow body has braces, even one statement.
- Short bodies MAY stay on one line when the formatter produces it, for example
  `if (mv < 0) { return prev; }`.
- `case` labels are indented inside `switch`.
- Two spaces before a trailing comment.
- LF line endings and a final newline.

### 2.3 Rules the formatter does not check

- Files MUST be UTF-8 with LF endings (`.gitattributes` sets `eol=lf`). Configure your editor so
  it does not write CRLF.
- No trailing whitespace, no more than one blank line in a row, no merge-conflict markers.
- One variable per declaration statement.
- Initialize a local where you declare it if the value is known. Zephyr style puts declarations at
  the top of the block, followed by one blank line; follow that in new code.
- Keep a formatting-only change out of a functional commit. Format only the lines you touch.

## 3. Files and layout

### 3.1 Directory structure

```text
firmware/
├── CMakeLists.txt        # globs src/**/*.c
├── Kconfig               # application options
├── prj.conf
├── boards/<board>.overlay
├── src/
│   ├── main.c
│   ├── common/           # shared helpers with no hardware access
│   ├── fsm/              # state machine and one file pair per state/region
│   ├── hs/               # project constants (thresholds.h)
│   ├── safety/           # watchdog, battery, VBUS lockout
│   └── ui/               # LED, button
└── tests/<module>/       # one ztest application per module
```

- Each module is one directory under `src/`. A `.c` file and its public `.h` file have the same
  base name and live in the same directory.
- Put a new subsystem (for example `ble/`, `sensor/`, `storage/`) in a new directory. Do not add
  generic `utils.c` or `helpers.c` files.
- `CMakeLists.txt` globs `src/*.c`, so a new `.c` file is in the build when it is in `src/`. Run
  CMake again after you add a file.

### 3.2 Header files

Every header MUST follow this template:

```c
#ifndef LED_H
#define LED_H

#include <stdint.h>

/* declarations */

#endif  // LED_H
```

- The include guard is `<FILE>_H` in upper case, and the `#endif` repeats it in a `//` comment.
  (Do not add `#pragma once`. The project uses guards.)
- A header MUST compile on its own: include what it uses, and do not depend on the include order
  of the `.c` file.
- A header declares only the public API. Put private types, `static` functions, and
  implementation-only includes in the `.c` file.
- Do not define variables or non-`static inline` functions in a header.
- Forward-declare a struct (`struct k_work;`) when a pointer is enough and the full include is
  heavy.

### 3.3 Include order

In a `.c` file:

1. The paired header (`"safety/safety.h"` in `safety/safety.c`). clang-format keeps it first.
2. One sorted block with project headers (`"module/file.h"`) and then system and Zephyr headers
   (`<...>`). clang-format sorts this block; `"` sorts before `<`.
3. Conditional includes last, inside their `#if`.

- Project includes MUST use the path from `src/`: `#include "fsm/state_machine.h"`. Do not use
  `../` paths.
- Include what you use. Do not rely on a header that something else includes for you.

## 4. Naming

All identifiers are `snake_case` except macros, Kconfig symbols, and enum constants, which are
`UPPER_SNAKE_CASE`. No Hungarian or type prefixes.

| Symbol | Convention | Example |
|---|---|---|
| Public function | `<module>_<verb/noun>` | `safety_init()`, `led_request()`, `fsm_post()` |
| File-local function | `static`, short descriptive name | `batt_read_hw()`, `reset_cause_read()` |
| File-local variable | `static`, descriptive | `batt_lvl`, `wdt_id` |
| Enum type | `<module>_<name>_e` | `led_pattern_e`, `state_event_e` |
| Enum constant | `<MODULE>_<NAME>_<VALUE>` | `LED_PAT_BEAT`, `STATE_EVENT_BATTERY_CHANGED` |
| Count sentinel | `<PREFIX>_COUNT`, last | `LED_PRIO_COUNT`, `FSM_TIMER_COUNT` |
| Struct | `struct <module>_<name>` (no typedef) | `struct led_slot` |
| Macro / constant | `<MODULE>_<NAME>` | `BATT_CRITICAL_MV`, `LED_FLASH_MS` |
| Shell command handler | `cmd_<name>` | `cmd_batt()` |
| Work / timer handler | `<name>_fn` or `<name>_handler` | `batt_work_fn()` |
| Kconfig symbol (new) | `HS_<NAME>` | `CONFIG_BENCH_ALLOW_USB` |
| Test | `test_<behaviour>` in `ZTEST(<suite>, ...)` | `test_no_chatter_low` |

### 4.1 Rules

- Every public symbol in a header MUST start with the module prefix. This is C: there are no
  namespaces, so the prefix prevents collisions with Zephyr and the SDK.
- New Kconfig symbols MUST use the `HS_` prefix. A symbol without a prefix can collide with an
  upstream Zephyr or NCS symbol. A reference to an undefined `CONFIG_` symbol does not cause a
  build error: `IS_ENABLED()` silently returns 0. Check that each `CONFIG_` name you use exists
  in `Kconfig`.
- **Units go in the name** for any physical quantity in a primitive type: `_mv`, `_ma`, `_ms`,
  `_us`, `_s`, `_hz`, `_pct`. Example: `period_ms`, `BATT_MARGIN_MV`. Do not mix units without an
  explicit conversion (`CONFIG_HS_MEASURE_INTERVAL_S * MSEC_PER_SEC`).
- Booleans and predicate functions read as a true statement: `inited`, `wdt_ok`,
  `safety_vbus_present()`, `battery_above_margin()`. Do not use inverted names such as
  `not_ready`.
- Name functions by what they do, including side effects: a function that can block has a name
  that says so (`*_wait`), and a function named like a query MUST NOT change state.
- Use full words for public APIs. Accepted abbreviations: `batt`, `lvl`, `ms`/`mv`/units, `wdt`,
  `fsm`, `ble`, `adc`, `gpio`, `isr`, `err`, `ev`, `cfg`, `prio`, `pat`. Add to this list in this
  document rather than inventing a new one in one file.

## 5. Types and interfaces

- Use `<stdint.h>` fixed-width types for registers, protocols, stored data, and anything with a
  defined size. Use `int` for errno-style returns and small loop counters. Use `size_t` for sizes
  and counts of memory.
- Use `bool` from `<stdbool.h>`, not `int`, for true/false.
- Use an enum for every closed set of values. Give the enum a `_COUNT` sentinel when code
  indexes arrays with it, and size those arrays with it.
- Every enum MUST be a typedef of an anonymous enum, named `<module>_<name>_e`:
  `typedef enum { ... } led_pattern_e;`.
  Do not declare a tagged `enum <name> { ... };`.
- Use a sentinel value (for example `BATT_UNKNOWN = -1`) only when it cannot be a valid value,
  and document it on the function that returns it.
- Mark pointer parameters `const` when the function does not write through them. Mark lookup
  tables `static const`.
- Do not expose module variables with `extern`. If one is unavoidable (for example
  `fsm_msgq`, so producers can use `k_msgq_put` directly), document who may write to it and from
  which context.
- Test hooks (for example `safety_set_batt_override()`) MUST be documented as test or shell hooks
  and SHOULD be guarded by Kconfig when they change safety behaviour.

## 6. Functions, errors, and assertions

### 6.1 Return values

- A function that can fail MUST return `int`: `0` on success, a negative errno (`-EINVAL`,
  `-EIO`, `-ENODEV`, `-EBUSY`, `-EPERM`, ...) on failure. This matches Zephyr.
- Document each return value with `@retval` (or `@return` when there is only one meaning).
- Check every return value that matters. When you ignore one on purpose, cast it to `(void)` and,
  if it is not obvious, say why:

  ```c
  (void)k_work_schedule(&batt_work, K_MSEC(BATTERY_PERIOD_MS)); /* already scheduled is fine */
  ```

- Do not continue after a required step fails, unless there is a documented fallback (as
  `safety_init()` does when the ADC is missing: it logs and keeps the level at OK).
- Output parameters are pointers, named for what they receive, and documented with `@param[out]`.
  Write to them only on success.

### 6.2 Assertions

- Use `__ASSERT(cond, "msg with %d context", value)` for invariants and preconditions that only
  internal code can violate, such as legal FSM predecessors.
- An assert condition MUST NOT have side effects. Asserts are compiled out when assertions are
  disabled.
- If a bad value can cause memory corruption even in a release build, add a runtime check as
  well as the assert.

### 6.3 Initialization

- Init functions MUST be safe to call twice (return the stored result of the first call), or the
  documentation MUST say that a second call is a bug.
- After an init failure the module MUST be in a defined state, and every public function MUST
  behave predictably in that state (for example do nothing, or return `-ENODEV`).

### 6.4 Logging

- Each module registers or declares a log module (`LOG_MODULE_REGISTER(safety, ...)` or
  `LOG_MODULE_DECLARE(fsm, ...)`).
- Log at the point that has the context, once. Do not log the same failure at every level of the
  call stack.
- Include the useful values: `LOG_WRN("task watchdog init failed (err %d)", err)`, not
  `LOG_WRN("failed")`.
- `LOG_ERR`: an operation failed. `LOG_WRN`: degraded, but continuing. `LOG_INF`: state changes
  that a person needs to see. `LOG_DBG`: detail for development.
- Do not log in a hot path or in an ISR at `INF` or higher. Do not log at every periodic tick when
  nothing changed.

## 7. Concurrency and execution context

This firmware runs code in several contexts: the main thread (FSM loop), the system work queue,
kernel timer expiry functions (ISR context), GPIO and input callbacks, and the shell thread.

- Each public function that is not safe from every context MUST say in its Doxygen comment
  where it may be called from. Example: "The function does not block" on `fsm_post()`.
- Code in ISR or timer-expiry context MUST NOT block: no `K_FOREVER`, no mutexes, no sleeping,
  no flash access. Use `K_NO_WAIT` and defer work with `k_work`.
- Protect state that more than one context touches:
  - `k_spinlock` when an ISR touches it.
  - `k_mutex` when only threads touch it (for example `batt_lock`).
  - `atomic_t` for single flags or counters.
- Keep lock regions short. Do not call code that can block while you hold a spinlock.
- Events into the state machine go through `fsm_post()`. Do not call
  `state_machine_process_event()` from anywhere except the main loop.
- Allocate kernel objects (`k_work_delayable`, `k_timer`, `k_msgq`, mutexes) statically with the
  `K_*_DEFINE` macros so their lifetime is the whole program.
- A callback that borrows a pointer MUST NOT keep it after the callback returns unless the
  owner guarantees the lifetime.
- The watchdog is a safety feature. Any code path that drives the sensor MUST run between
  `safety_drive_begin()` and `safety_drive_end()` and feed it at least every `DRIVE_WDT_MS`.

## 8. Memory, integers, and data

- No heap (`malloc`, `k_malloc`, `k_heap`) in the firmware. Use static or stack storage. A
  deviation needs a stated reason and a bounded size.
- Keep large buffers off thread stacks. Check stack usage with the thread analyzer when you add
  work to a thread or work handler.
- Use `sizeof(buf)` or `ARRAY_SIZE(arr)` for bounds, never a repeated literal.
- Check every array index that comes from outside the module (enum values from callers, shell
  arguments) before you use it.
- Integer arithmetic:
  - Widen before you multiply if the result can exceed the operand type.
  - Check for a negative value before you cast signed to unsigned.
  - Check a narrowing cast when the value can exceed the target range.
  - Never divide by a value that can be zero.
- Floating point: do not compare computed values with `==`; use a tolerance that matches the
  measurement. Check for NaN on values from computation or external input. Prefer integer
  millivolts and milliseconds where precision allows.
- Data that is stored to flash or sent over BLE MUST have a defined byte layout (fixed-width
  fields, explicit endianness with `sys_put_le16()` and similar). Do not write a C struct straight
  to flash or to the radio.

## 9. Control flow and expressions

- Use early returns for invalid input and unmet preconditions.
- `switch` on an enum lists every value and has no `default:` when the set is closed, so the
  compiler warns when you add a value. Use `default:` only when unknown values are expected, and
  handle them.
- Intentional fallthrough MUST use `__fallthrough;` (Zephyr's attribute macro). Labels that share
  a body do not need it.
- No assignment inside an `if` or `while` condition.
- Parenthesize mixed `&&` and `||`. If a condition is hard to read, give part of it a name with a
  `const bool`.
- No nested ternary operators. A single ternary that selects between two simple values is fine.
- No comma operator outside a `for` header.
- Do not change the same variable twice in one expression, and do not depend on argument
  evaluation order.
- Every loop that can wait on hardware MUST have a timeout or a bound.

## 10. Preprocessor, Kconfig, and devicetree

- Prefer `IS_ENABLED(CONFIG_X)` in normal `if` statements over `#ifdef`, so both branches compile
  in every build. Use `#if` when the code cannot compile without the option (for example a
  missing header or a devicetree node).
- Use devicetree macros (`DT_ALIAS`, `GPIO_DT_SPEC_GET`, `ADC_DT_SPEC_GET`) for hardware. Do not
  hard-code pin numbers or peripheral addresses. Handle a missing node in a way that still
  builds on `native_sim`.
- Put tunable numbers (thresholds, timeouts, periods) in `hs/thresholds.h` or in Kconfig, with
  units in the name. No magic numbers in logic.
- A Kconfig option that a user may change needs a `help` text that says what it does and its
  unit.
- Macros: `UPPER_SNAKE_CASE`, every argument and the whole body in parentheses, no side-effect
  arguments. Prefer a `static inline` function when a macro is not needed.
- No `#if 0` blocks and no commented-out code. Git keeps the history.

## 11. Comments and documentation

- Every public function in a header has a Doxygen block: `@brief`, `@param[in]` /
  `@param[out]` / `@param[in,out]` for each parameter, and `@return` or `@retval`. Static
  functions in a `.c` file get the same block if they are not trivial.
- Write comments in short, plain sentences in the present tense ("The function posts ..."). Say
  what the code guarantees, its units, and its context restrictions.
- Comments explain *why* and *constraints*, not a repeat of the next line:

  ```c
  /*
   * Arm the hardware fallback now. The nRF WDT keeps running across a soft reset and cannot
   * be stopped, so it has to be fed from boot, not only from the first measurement.
   */
  ```

- When behaviour changes, update the comment in the same commit. A wrong comment is worse than no
  comment.
- New TODOs use `// TODO(<issue # or owner>): <specific action>.` A TODO without an action is not
  allowed. Stub code (for example `fsm_stub()`) MUST say that it is temporary and what replaces
  it.
- Hardware facts (from a datasheet, errata, or the nRF docs) get a reference in the comment.

## 12. Testing

- Each module with logic has a ztest application in `firmware/tests/<module>/` that builds for
  `native_sim/native/64`, and is listed in `.vscode/settings.json` for the nRF Connect extension.
- Test pure functions directly. Put hardware-independent logic in a function that takes inputs and
  returns outputs, so that the test does not need the board.
- Test boundaries and edge cases: exactly at a threshold, one below, one above, the unknown or
  error input, and repeated inputs (no chatter).
- An assert message in a test says what was fed in and what was expected.
- Before you push, both CI jobs MUST pass locally where possible:

  ```bash
  west build -p always -b nrf52840dk/nrf52840 firmware
  ```

  ```bash
  west twister -T firmware/tests -p native_sim/native/64 --inline-logs
  ```

- A bug fix SHOULD come with a test that fails without the fix.
- Things that CI cannot test (power draw, the real watchdog, BLE with a phone) MUST be tested on
  the board for changes that affect them. Say in the PR what you tested on hardware and what you
  did not.

## 13. Commits and review

### 13.1 Commits

- One logical change per commit. Formatting-only changes go in their own commit.
- Subject line in the imperative, capitalized, no trailing period, about 50 characters
  ("Add STATE_EVENT_BATTERY_CHANGED", "Debounce button and use a 2s long press").
- Add a body when the *why* is not obvious from the subject.
- Do not commit build output (`firmware/build/`), editor files outside `.vscode/settings.json`,
  or secrets.

### 13.2 Before you submit

- [ ] clang-format 18.1.8 reports no changes.
- [ ] The firmware builds for `nrf52840dk/nrf52840` and twister passes on `native_sim`.
- [ ] Every new public function has a module prefix and a Doxygen block.
- [ ] Every `CONFIG_` symbol that the code uses exists in `Kconfig` (or upstream).
- [ ] Every failing call is handled or cast to `(void)` on purpose.
- [ ] State that is shared between contexts is protected, and ISR paths do not block.
- [ ] No heap, no magic numbers, units in names.
- [ ] Comments and the README match the new behaviour.
- [ ] Hardware testing (or its absence) is stated.

### 13.3 Review priorities

Review in this order: (1) correctness and device safety, (2) concurrency and context, (3) error
handling, (4) interfaces and module boundaries, (5) tests, (6) readability. The formatter handles
layout, so do not spend review time on it.

---

## 14. Exceptions and changes to this document

- A deviation from a SHOULD rule needs a short reason in the commit message or PR.
- A deviation from a MUST rule needs a comment at the code that says which rule and why, and
  agreement in review.
- Change this document by PR. When a rule maps to a tool setting (`.clang-format`, CI), change
  both in the same PR.
- When a pattern shows up in several places and works, add it here instead of letting it spread
  without a record.

> **Design test:** can a new team member tell what this code owns, which context it runs in, how
> it fails, and what must stay true, without reading other files? If not, fix the names, the
> interface, or the comment.
